# Webhook Events

This page is for developers building webhook handlers for Meld crypto transactions. It documents every event type, the payload schema, and how to map events back to your transaction in your system. Webhooks provide real-time notifications when transaction statuses change. Instead of polling for updates, Meld sends HTTP POST requests to your configured endpoint whenever events occur. Use webhooks as triggers to call `GET /payments/transactions/{transactionId}` to fetch the latest details on the transaction. For a headless sell (offramp) order, also read the order's status, as [Track the order](/docs/stablecoins/virtual-account-integration/payouts#7-track-the-order) describes.

## Benefits

* **Real-time updates**: Immediate notification of status changes
* **Reduced latency**: No polling delays
* **Lower infrastructure cost**: No need for frequent API calls
* **Reliable delivery**: Built-in retry mechanisms

## Event Structure

All webhook events share the same base structure:

### Common Attributes

| Field             | Type           | Description                                            |
| ----------------- | -------------- | ------------------------------------------------------ |
| `eventType`       | String         | Type of event (e.g., `TRANSACTION_CRYPTO_PENDING`)     |
| `eventId`         | String         | Meld's unique identifier for this event                |
| `timestamp`       | OffsetDateTime | When the event was created                             |
| `accountId`       | String         | Your Meld account identifier                           |
| `profileId`       | String         | Webhook profile responsible for sending this event     |
| `version`         | Date           | Payload version (e.g., `2023-01-30`)                   |
| `payload`         | Object         | Event-specific data containing transaction details     |

### Payload Fields

The `payload` object contains transaction-specific information:

| Field                      | Type   | Description                                            |
| -------------------------- | ------ | ------------------------------------------------------ |
| `accountId`                | String | Meld account identifier                                |
| `customerId`               | String | Meld's internal customer identifier                    |
| `externalCustomerId`       | String | Your customer ID (if provided during session creation) |
| `externalSessionId`        | String | Your session ID (if provided during session creation)  |
| `paymentTransactionId`     | String | Meld's unique transaction identifier                   |
| `paymentTransactionStatus` | String | Current transaction status                             |
| `transactionType`          | String | `CRYPTO_PURCHASE`, `CRYPTO_SELL`, or `CRYPTO_TRANSFER` |
| `sessionId`                | String | Meld's internal session identifier                     |
| `orderId`                  | String | The headless order the transaction belongs to. Absent when there is none |
| `externalOrderId`          | String | Your reference for that order, or `null` |
| `orderStatus`              | String | The sell order's status when the event was created. Sell (`CRYPTO_SELL`) orders only |
| `errorCode`                | String | Why the sell order is `FAILED`, `CANCELLED`, `EXPIRED`, `REFUNDED` or `UNDER_REVIEW`, or `null`. Sell orders only |
| `errorText`                | String | `errorCode` in words, or `null`. Sell orders only |

The order fields need webhook version `2026-09-01` or later: see [Webhook version](/docs/stablecoins/virtual-account-integration/payouts#webhook-version). On that version, `paymentTransactionId`, `paymentTransactionStatus`, `externalOrderId`, `errorCode` and `errorText` are always sent, as `null` when empty.


<Warning>
**Note**: For `PENDING_CREATED` status, `sessionId` and `externalSessionId` may be missing as the transaction hasn't been tied to a session yet. You can safely ignore these early-stage webhooks if needed.
</Warning>


## Event Types

### `TRANSACTION_CRYPTO_PENDING`

Triggered when a user starts the payment process (logged in, completed KYC).

```json
{
  "eventType": "TRANSACTION_CRYPTO_PENDING",
  "eventId": "AAsuLXHXD3mS1cjNBuHHzv",
  "timestamp": "2022-02-24T16:36:41.717262Z",
  "accountId": "W2aRZnYGPwhBWB94iFsZus",
  "profileId": "W9ka8vLE4ufBkSg3BEciZb",
  "version": "2023-01-30",
  "payload": {
    "requestId": "f07f1accb7404aec9bd9a5d64975eed1",
    "accountId": "W2aRZnYGPwhBWB94iFsZus",
    "paymentTransactionId": "W9k9Tg12BFk1i68WpQYQY8",
    "customerId": "W9k9TfNSJRZ6rDBe95bUA2",
    "externalCustomerId": "customer_1234443",
    "externalSessionId": "test_session1",
    "paymentTransactionStatus": "PENDING",
    "transactionType": "CRYPTO_PURCHASE",
    "sessionId": "WeQBQxGxq3AyHdcaoUDoAJ"
  }
}
```

### `ORDER_CRYPTO_FAILED`

Triggered when a headless sell (offramp) order ends without a payout: before any deposit (`EXPIRED`, `FAILED` or `CANCELLED`), whether or not the order has a transaction, or with its deposit owed back on an order that has no transaction (`REFUNDED`). The payload always has the `2026-09-01` shape, whatever your endpoint's version. The transaction fields are `null` when the order has no transaction. Read the order with `GET /crypto/order/{orderId}/status` when it arrives.

```json
{
  "eventType": "ORDER_CRYPTO_FAILED",
  "eventId": "Wg3nH8sQe2PvLk7cRt5YbA",
  "timestamp": "2026-11-10T14:02:11.204518Z",
  "accountId": "W2aRZnYGPwhBWB94iFsZus",
  "profileId": "W9ka8vLE4ufBkSg3BEciZb",
  "version": "2026-09-01",
  "payload": {
    "requestId": "a1c94e0f5b2d4f7e8c3b6a9d0e1f2a3b",
    "accountId": "W2aRZnYGPwhBWB94iFsZus",
    "paymentTransactionId": null,
    "customerId": "W9kL817BBS7bNEwxAZaX4z",
    "externalCustomerId": "customer_9888888",
    "paymentTransactionStatus": null,
    "transactionType": "CRYPTO_SELL",
    "orderId": "WfR7abcDEF12345xyz9876",
    "externalOrderId": "sell-order-123",
    "orderStatus": "EXPIRED",
    "errorCode": "CRYPTO_DEPOSIT_MISSING",
    "errorText": "No deposit reached the order before it expired"
  }
}
```

An endpoint that subscribes to `ORDER_CRYPTO_FAILED` by name doesn't also get `TRANSACTION_CRYPTO_FAILED` for an order that ended before any deposit. An endpoint that subscribes to every event gets both.

### `CUSTOMER_KYC_STATUS_CHANGE`

This is sent when you have Meld KYC a user and the user's KYC status is updated, and when a provider Meld shared the user's KYC with reports its verdict. Read more in [Meld KYCes the user](/docs/stablecoins/unified-kyc/meld-kyces-the-user) and [KYC levels](/docs/stablecoins/unified-kyc/kyc-levels).

```json
{
    "eventType": "CUSTOMER_KYC_STATUS_CHANGE",
    "eventId": "4cWK83avakzy8jG4ztmBUk",
    "timestamp": "2026-02-25T18:55:08.968360756Z",
    "accountId": "W2aRZnYGPwhBWB94iFsZus",
    "profileId": "WmZ1rqsv532RYW9ELxM4eo",
    "version": "2026-02-02",
    "payload": {
      "requestId": "4456e4e9b0174c53b962227df6766ca7",
      "customerId": "W9kL817BBS7bNEwxAZaX4z",
      "serviceProvider": "SUMSUB",
      "status": "APPROVED",
      "statusUpdatedAt": "2026-02-25T18:55:08.960052Z",
      "level": "LEVEL_2",
      "approvedLevel": "LEVEL_2"
    }
}
```

| Field | Description |
| --- | --- |
| `customerId` | The Meld customer |
| `serviceProvider` | The KYC provider, `SUMSUB` |
| `status` | The customer's Unified KYC status: `PENDING`, `APPROVED`, `REJECTED`, `EXPIRED` or `UNKNOWN` |
| `statusUpdatedAt` | When the status changed |
| `level` | The [KYC level](/docs/stablecoins/unified-kyc/kyc-levels) `status` is for: `LEVEL_1`, `LEVEL_2` or `LEVEL_3`. Absent when Meld doesn't know it |
| `approvedLevel` | The highest level the customer is approved at. It stays while a higher level is in review, and is absent when nothing is approved |
| `kycRecipient` | Present only when a provider Meld shared the customer's KYC with reports its verdict: `serviceProvider` is that provider, and `status` its verdict, such as `PENDING`, `APPROVED` or `REJECTED`. `status`, `level` and `approvedLevel` around it still describe the customer's Unified KYC |

When a customer steps up, you receive `status: PENDING` with the new `level`, while `approvedLevel` keeps the level they're already approved at:

```json
"payload": {
  "customerId": "W9kL817BBS7bNEwxAZaX4z",
  "serviceProvider": "SUMSUB",
  "status": "PENDING",
  "statusUpdatedAt": "2026-10-29T18:55:08.960Z",
  "level": "LEVEL_2",
  "approvedLevel": "LEVEL_1"
}
```

A provider's verdict on a share arrives as its own event:

```json
"payload": {
  "customerId": "W9kL817BBS7bNEwxAZaX4z",
  "serviceProvider": "SUMSUB",
  "status": "APPROVED",
  "statusUpdatedAt": "2026-10-29T19:02:41.117Z",
  "level": "LEVEL_2",
  "approvedLevel": "LEVEL_2",
  "kycRecipient": { "serviceProvider": "BANXA", "status": "APPROVED" }
}
```

Read `kycRecipient` before `status`: an event that carries it is about that provider, not a second Unified KYC approval.

## Implementation Tips

**Response Requirements**: Your webhook endpoint must return a 2xx HTTP status code to acknowledge receipt.

**Retry Logic**: Meld automatically retries failed webhook deliveries with exponential backoff.

**Idempotency**: Use `eventId` to handle duplicate deliveries safely.

**Error Handling**: Implement graceful error handling for malformed or unexpected webhook payloads.
