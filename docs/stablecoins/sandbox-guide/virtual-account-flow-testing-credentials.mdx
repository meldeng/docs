This page walks developers through end-to-end sandbox testing of the Virtual Account flow: SumSub shared KYC, the provider-hosted questionnaire step, quote creation, provisioning, and deposit simulation for Noah, Due Network, and Brale. For the product overview and production wiring, see the [Virtual Account Integration Guide](/docs/stablecoins/virtual-account-integration).

<Warning>
  **Sandbox limitation.** Provider sandboxes do not move real money.

  - **Onramp** can be completed end to end for Noah and Due Network via the deposit simulator. Brale has no sandbox deposit simulator, so there you stop at creating the virtual bank account.
  - **Offramp** only reaches a deposit address. There is no way to settle an offramp in sandbox.
</Warning>

Set these once and reuse them in every call below:

```bash
export MELD_BASE_URL="https://api-sb.meld.io"
export MELD_API_KEY="<your-sandbox-api-key>"
export MELD_VERSION="2026-05-01"
```

## Before you start

<Steps>
  <Step title="Create a customer">
    Create a `customerId` via `POST /accounts/customers` (see Step 1 of the [integration guide](/docs/stablecoins/virtual-account-integration/payins)). If you need a **business** customer for KYB testing, contact Meld.

    ```bash
    curl -X POST "$MELD_BASE_URL/accounts/customers" \
      -H "Authorization: BASIC $MELD_API_KEY" \
      -H "Content-Type: application/json" \
      -d '{
        "externalCustomerId": "your-internal-user-id-123"
      }'
    ```
  </Step>
  <Step title="Complete KYC">
    Complete SumSub shared KYC (below), then the provider-hosted questionnaire (below) for each provider you plan to use. Wait for the **provider's** KYC to reach `APPROVED`, not just SumSub's.
  </Step>
  <Step title="Enable whitelabel mode on your account">
    Ask Meld support to enable **whitelabel mode** (`headlessOnrampsEnabled`). It is account-wide, not per-provider, but without it every virtual account call fails with `403 WHITELABEL_NOT_ENABLED` even for a fully KYC-approved customer.
  </Step>
  <Step title="Check supported currencies and rails">
    Call `GET /service-providers/properties/crypto-currencies` with `serviceProviders=` and `categories=CRYPTO_VIRTUAL_ACCOUNT_ONRAMP` (or `CRYPTO_VIRTUAL_ACCOUNT_OFFRAMP`) to see what's available in sandbox for your target provider.
  </Step>
</Steps>

## SumSub shared KYC

One SumSub applicant approval gets reused across providers. The customer verifies identity once, and Meld shares the result to each provider you name. For the full sandbox KYC walkthrough, see [KYC testing → Meld KYCes the user](/docs/stablecoins/sandbox-guide/kyc-testing).

```bash
curl -X POST "$MELD_BASE_URL/accounts/customers/$CUSTOMER_ID/kyc/initiate" \
  -H "Authorization: BASIC $MELD_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "serviceProvider": "SUMSUB",
    "mode": "HOSTED_URL",
    "kycShareProviders": ["NOAH", "DUENETWORK"]
  }'
```

- **`kycShareProviders`** triggers the fan-out. You can also share one provider at a time and repeat the call for the other; either works. If a provider was already shared, the `POST` returns `409` — retry the same call as a `PATCH` to re-issue.
- **`mode`** can also be `TOKEN_IMPORT` (customer already has a SumSub applicant or token) or, via the multipart variant, `RAW_DATA_IMPORT`.
- For `HOSTED_URL` mode, the response includes a hosted SumSub `url`. Send the customer there to complete identity verification.

Check status:

```bash
curl "$MELD_BASE_URL/accounts/customers/$CUSTOMER_ID" \
  -H "Authorization: BASIC $MELD_API_KEY"
```

Look at `serviceProviderCustomers[].kyc.status` for `SUMSUB` **and** for each provider you shared to. You want the **provider's** status at `APPROVED`, not just SumSub's.

## The provider-hosted questionnaire (Noah and Due)

<Warning>
  **Neither Noah nor Due is pre-filled by Meld.** Meld only passes the SumSub verification result over (plus some standard agreement acceptances for Noah). It never submits real questionnaire answers on the customer's behalf. Due's own KYC-share request even has dedicated fields for prefilled answers, and Meld always sends them empty.

  For both providers, a human has to open a provider-hosted page and fill it in themselves. There is no way to skip this step programmatically.
</Warning>

**How to tell if it's still outstanding.** On the same `GET /accounts/customers/{customerId}` call above, look at that provider's entry in `serviceProviderCustomers[]`:

```json
{
  "serviceProvider": "NOAH",
  "kyc": {
    "status": "PENDING",
    "additionalInfo": {
      "HostedURL": "https://onboarding.noah.com/...",
      "missingSteps": ["..."]
    }
  }
}
```

The questionnaire is still outstanding if `kyc.additionalInfo.HostedURL` is present **and** `kyc.status` is not `APPROVED`, `REJECTED`, or `EXPIRED`. There is no separate "questionnaire complete" flag; the presence of `HostedURL` plus the coarse KYC status is the only signal available. `status` moves to `APPROVED` or `REJECTED` asynchronously once the provider's webhook fires after the customer finishes the hosted page. There is no intermediate "submitted, awaiting review" state.

**If the link is stale** (for example, Due's hosted-session tokens expire), refresh it:

```bash
curl -X PATCH "$MELD_BASE_URL/accounts/customers/$CUSTOMER_ID/kyc/initiate" \
  -H "Authorization: BASIC $MELD_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "kycShareProviders": ["NOAH"]
  }'
```

Then `GET` the customer again for the fresh `HostedURL`.

<Note>
  **Sandbox note.** The hosted step cannot be automated. If you are scripting sandbox tests, you need a pre-provisioned test customer who has already completed the real hosted questionnaire with each provider. There is no API-level bypass in a customer-facing environment.
</Note>

<Warning>
  **Known gotcha (Due).** Due also runs its own separate KYC/KYB approval independent of this questionnaire. A customer can complete the hosted page and still be rejected by Due at order time (`err_kyc_not_passed`) if Due's own account import hasn't completed on their side. If it persists, contact Meld to check.
</Warning>

## Create a quote

This is the shared headless quote endpoint, not a virtual-account-only one. Always include `paymentMethodType`, or Meld falls back to Uphold's card quote instead of Noah's or Due's bank quotes.

```bash
curl -X POST "$MELD_BASE_URL/payments/crypto/quote?includeSwap=true&integrationMode=HEADLESS" \
  -H "Authorization: BASIC $MELD_API_KEY" \
  -H "Meld-Version: $MELD_VERSION" \
  -H "Content-Type: application/json" \
  -d '{
    "customerId": "'"$CUSTOMER_ID"'",
    "countryCode": "US",
    "sourceCurrencyCode": "USD",
    "destinationCurrencyCode": "USDC",
    "sourceAmount": 100,
    "paymentMethodType": "ACH"
  }'
```

Swap in the provider's test values from the tables above for Due (`EUR` / `USDT_TRON` / `SEPA`) or Brale (`USD` / `USDC` / `LOCAL_BANK_TRANSFER`). Note: Brale returns a fixed 1:1 rate.

## Provision the virtual account

```bash
curl -X POST "$MELD_BASE_URL/payments/virtual-account/deposit-instructions" \
  -H "Authorization: BASIC $MELD_API_KEY" \
  -H "Meld-Version: $MELD_VERSION" \
  -H "X-Idempotency-Key: $(uuidgen)" \
  -H "Content-Type: application/json" \
  -d '{
    "customerId": "'"$CUSTOMER_ID"'",
    "serviceProvider": "NOAH",
    "paymentMethodType": "ACH",
    "sourceCurrencyCode": "USD",
    "destinationCurrencyCode": "USDC",
    "destinationWalletAddress": "0x1ab6f09b58ef63b38cee48af542561c75f2cd44c"
  }'
```

Returns `201` with bank or IBAN coordinates once provisioned, or `202` with a `Retry-After` header while the provider is still async-provisioning. Poll with the **same** `X-Idempotency-Key`.

<Note>
  If Due returns `403` for terms-not-accepted, re-sync KYC via the `PATCH /kyc/initiate` call above to obtain a fresh terms URL, rather than retrying the provisioning call blindly.
</Note>

## Simulate a deposit

You cannot send real fiat to a sandbox virtual account, so there is nothing to trigger settlement. Call the endpoint below instead: Meld creates a test deposit into the standing account you fetched with `POST /payments/virtual-account/deposit-instructions`, and the provider's normal webhooks settle it exactly as in production.

| Provider | Deposit simulation | `paymentMethodType` | Fiat |
| --- | --- | --- | --- |
| Noah | Supported | `ACH` | USD |
| Due Network | Supported | `SEPA` | EUR (non-US customer) |
| Brale | Not supported | — | — |

<Warning>
  Sandbox only. In production this endpoint returns `404`. Onramp (payin) only. There is no offramp equivalent; an offramp cannot be settled in sandbox.
</Warning>

**Endpoint:** `POST /payments/mock/headless/virtual-account/simulate-deposit`

Repeat the provider, rail, currencies, and destination wallet from your deposit instructions, and set `amount` to the amount you want deposited.

```bash
curl -X POST "$MELD_BASE_URL/payments/mock/headless/virtual-account/simulate-deposit" \
  -H "Authorization: BASIC $MELD_API_KEY" \
  -H "Meld-Version: $MELD_VERSION" \
  -H "Content-Type: application/json" \
  -d '{
    "customerId": "'"$CUSTOMER_ID"'",
    "serviceProvider": "NOAH",
    "paymentMethodType": "ACH",
    "sourceCurrencyCode": "USD",
    "destinationCurrencyCode": "USDC",
    "destinationWalletAddress": "0x1ab6f09b58ef63b38cee48af542561c75f2cd44c",
    "amount": "25"
  }'
```

For **Due Network**, swap in `"serviceProvider": "DUENETWORK"`, `"paymentMethodType": "SEPA"`, `"sourceCurrencyCode": "EUR"`, and a token like `USDT_TRON`. Leave `network` out entirely for both providers; it is a Uphold-only field.

Under the hood Meld dispatches per provider: Noah's own sandbox simulator, Due's sandbox payin. Either way the deposit settles asynchronously via webhook, not in the response.

### Confirm settlement

Settlement is asynchronous, so the transaction does not exist yet when the simulate call returns. Normally you react to the `TRANSACTION_CRYPTO_*` webhooks you subscribed to in [Payins](/docs/stablecoins/virtual-account-integration/payins). If you are scripting a test, or you have not set up a sandbox webhook endpoint, poll instead until a **new** transaction reads `SETTLED`. Typically 30 to 90 seconds for Noah, sometimes longer for Due.

**Endpoint:** `GET /payments/transactions?customerIds={customerId}`

```bash
curl "$MELD_BASE_URL/payments/transactions?customerIds=$CUSTOMER_ID" \
  -H "Authorization: BASIC $MELD_API_KEY"
```

Abridged (a transaction carries many more fields — see [Payins → Fetch the full transaction](/docs/stablecoins/virtual-account-integration/payins#fetch-the-full-transaction) for the full shape):

```json
{
  "transactions": [
    {
      "id": "WmZpNL9YBPeEKG4vJkwG9Q",
      "serviceProvider": "NOAH",
      "transactionType": "CRYPTO_PURCHASE",
      "status": "SETTLED",
      "sourceAmount": 25.0,
      "sourceCurrencyCode": "USD"
    }
  ]
}
```

### Troubleshooting

| Response | Cause |
| --- | --- |
| `403 WHITELABEL_NOT_ENABLED` | Whitelabel mode is not enabled for your account. Contact Meld. |
| `403 KYC_NOT_COMPLETED` | The provider's KYC for this customer is not `APPROVED`. Recheck the provider-hosted questionnaire step above. |
| `400` with Due's `err_tos_not_accepted` | The customer has not accepted Due Network's terms. Refresh via `PATCH /kyc/initiate`. |
| `400 ... currently supports only ...` | That provider has no sandbox deposit simulator (for example, Brale). |
| `404` | You are calling production, where this endpoint does not exist. |
| `200` but nothing settles | The provider accepted it and the webhook is in flight. Keep polling. |

## Testing tips

- **Wallet addresses:** any valid address for the token's chain. Some providers validate that the address format matches (for example, a TRON address for `USDT_TRON`).
- **Start with the onramp (buy) flow.** It is the most complete path in sandbox.
- **Discover currencies and rails:** call `GET /service-providers/properties/crypto-currencies` with the provider name and the relevant category to see what is available in sandbox.
- **Idempotency:** include `X-Idempotency-Key` on order and provisioning requests so you can safely retry without creating duplicates.
- **Webhooks:** `TRANSACTION_CRYPTO_PENDING` and friends may or may not fire in sandbox depending on the provider. If yours do not arrive, poll `GET /payments/transactions` instead — see [Simulate a deposit](#simulate-a-deposit).
