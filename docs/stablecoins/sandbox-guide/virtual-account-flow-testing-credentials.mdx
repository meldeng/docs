This page is a self-contained sandbox walkthrough of the Virtual Account flow. Work through it top to bottom and you will finish with a settled onramp transaction. Every command below is copy-pasteable as written — the only thing you supply is your sandbox API key.

For the product overview and production wiring, see the [Virtual Account Integration Guide](/docs/stablecoins/virtual-account-integration).

## What you can and cannot test in sandbox

Provider sandboxes do not move real money, so not every path can be completed. Read this before you start, so you know where each flow is expected to stop.

| Flow | Sandbox outcome |
| --- | --- |
| **Onramp — Noah** | Completes end to end. The deposit simulator settles the transaction. |
| **Onramp — Due Network** | Completes end to end where Due is enabled and KYC-shared for your customer. |
| **Onramp — Brale** | Stops at the virtual bank account. Brale has no sandbox deposit simulator. |
| **Offramp — all providers** | Stops at the deposit address. **There is no way to settle an offramp in sandbox** — no simulator exists for it, and the provider never receives crypto. |

<Warning>
  **Not covered by this page.** These are separate product surfaces with their own sandbox guides, and none can be exercised from the Virtual Account flow: fiat card and ACH payments ([Payments Stack](/docs/payments-stack/fiat-payment-testing-guide/card-testing-guide)), [Bank Linking](/docs/bank-linking/testing-and-debugging/bank-linking-sandbox-testing-guide), and headless Apple Pay ([Mercuryo](/docs/stablecoins/white-label-api-integration/headless-apple-pay)).
</Warning>

<Note>
  **What has been verified against sandbox.** The Noah onramp path below — customer lookup, KYC re-share, quote, provisioning, deposit simulation, and settlement — was run end to end and is confirmed working.

  The **Due Network** and **Brale** values in [Provider test values](#provider-test-values) have **not** been re-verified. On the account used to check this page, Due's KYC share sat at `PENDING` with its hosted questionnaire outstanding — which cannot be automated — so every Due call returned `403 KYC_NOT_COMPLETED`, and Brale was not enabled at all. Treat the Due SEPA rail, the Due offramp, and Brale's fixed 1:1 rate as documented but unconfirmed. If you hit a discrepancy, tell your Meld contact.
</Note>

## Prerequisites

<Steps>
  <Step title="A sandbox API key">
    From the Meld dashboard, **Developer → API keys**, in the **sandbox** environment. Sandbox and production keys are not interchangeable.
  </Step>
  <Step title="curl and jq">
    `jq` is only used to pull one id out of a response. On macOS it ships with the OS; on Debian or Ubuntu, `apt install jq`.
  </Step>
  <Step title="Whitelabel mode enabled on your account">
    Ask Meld support to enable **whitelabel mode** (`headlessOnrampsEnabled`). It is account-wide rather than per-provider, and without it every virtual account call fails with `403 WHITELABEL_NOT_ENABLED`, even for a fully KYC-approved customer.
  </Step>
  <Step title="At least one virtual-account provider enabled">
    Noah is the one this guide uses. Ask Meld support to confirm it is enabled on your sandbox account.
  </Step>
</Steps>

## Step 1 — Set up your shell

Paste your sandbox key into the first line. Everything after this is copy-paste.

```bash
export MELD_API_KEY="<your-sandbox-api-key>"
export MELD_BASE_URL="https://api-sb.meld.io"
export MELD_VERSION="2026-05-01"
```

Your sandbox account includes a pre-created customer that is already through SumSub KYC and onboarded with the virtual account providers. Resolve it to a `customerId` and keep it in your shell:

```bash
export CUSTOMER_ID=$(curl -s "$MELD_BASE_URL/accounts/customers?externalCustomerId=MELD_EXTERNAL_CUSTOMER_ID" \
  -H "Authorization: BASIC $MELD_API_KEY" \
  -H "Meld-Version: $MELD_VERSION" | jq -r '.customers[0].id')
echo "$CUSTOMER_ID"
```

**Expected:** a base58 id such as `WmYNx6LnmqasLfcp8HngoD`. If you get `null`, the pre-created customer is not on your account — create your own using [Using your own customer](#using-your-own-customer) instead.

<Note>
  The pre-created customer lets you skip customer creation, SumSub KYC, and the provider-hosted questionnaire — the three steps that cannot be automated. That is the fastest route to a settled transaction. To exercise the full onboarding path yourself, see [Using your own customer](#using-your-own-customer).
</Note>

## Step 2 — Confirm the customer is ready

```bash
curl -s "$MELD_BASE_URL/accounts/customers/$CUSTOMER_ID" \
  -H "Authorization: BASIC $MELD_API_KEY" \
  -H "Meld-Version: $MELD_VERSION" | jq '.serviceProviderCustomers[] | {serviceProvider, kycStatus: .kyc.status}'
```

**Expected:** `200`, and every provider you intend to use reads `"kycStatus": "APPROVED"`:

```json
{ "serviceProvider": "SUMSUB", "kycStatus": "APPROVED" }
{ "serviceProvider": "NOAH", "kycStatus": "APPROVED" }
{ "serviceProvider": "DUENETWORK", "kycStatus": "PENDING" }
```

You want the **provider's** status at `APPROVED`, not just SumSub's. In the response above only Noah is usable: `DUENETWORK` is shared but still `PENDING`, so a Due call would fail with `403 KYC_NOT_COMPLETED` until its hosted questionnaire is finished — see [Using your own customer](#using-your-own-customer).

## Step 3 — Get a quote

This is the shared headless quote endpoint, not a virtual-account-only one. Always include `paymentMethodType`, or Meld falls back to a card quote instead of the bank quotes the virtual account flow needs.

```bash
curl -s -X POST "$MELD_BASE_URL/payments/crypto/quote?includeSwap=true&integrationMode=HEADLESS" \
  -H "Authorization: BASIC $MELD_API_KEY" \
  -H "Meld-Version: $MELD_VERSION" \
  -H "Content-Type: application/json" \
  -d '{
    "customerId": "'"$CUSTOMER_ID"'",
    "countryCode": "US",
    "sourceCurrencyCode": "USD",
    "destinationCurrencyCode": "USDC",
    "sourceAmount": 100,
    "paymentMethodType": "ACH"
  }' | jq '.quotes[] | {serviceProvider, destinationAmount, kycMode, integrationMode}'
```

**Expected:** `200` with at least one quote. `serviceProvider` is the value you carry into the next step:

```json
{
  "serviceProvider": "NOAH",
  "destinationAmount": 97.971552,
  "kycMode": "ASYNC",
  "integrationMode": "HEADLESS"
}
```

An empty `quotes` array with `NO_VALID_QUOTES` means no provider serves that corridor and rail for your account — check your values against [Provider test values](#provider-test-values).

<Note>
  This endpoint also accepts `externalCustomerId` in place of `customerId`, which is convenient if you have not resolved the Meld id yet. The provisioning and simulation endpoints in Steps 4 and 5 do **not** — they take `customerId` only.
</Note>

## Step 4 — Provision the virtual account

This returns the standing bank details your customer would send fiat to. Fetch it once per customer, provider, payment method, currency pair, and destination wallet — it is reusable, not per-transaction.

```bash
curl -s -X POST "$MELD_BASE_URL/payments/virtual-account/deposit-instructions" \
  -H "Authorization: BASIC $MELD_API_KEY" \
  -H "Meld-Version: $MELD_VERSION" \
  -H "X-Idempotency-Key: $(uuidgen)" \
  -H "Content-Type: application/json" \
  -d '{
    "customerId": "'"$CUSTOMER_ID"'",
    "serviceProvider": "NOAH",
    "paymentMethodType": "ACH",
    "sourceCurrencyCode": "USD",
    "destinationCurrencyCode": "USDC",
    "destinationWalletAddress": "0x1ab6f09b58ef63b38cee48af542561c75f2cd44c",
    "countryCode": "US"
  }' | jq '{depositInstructionsId, receivingBankInformation}'
```

**Expected:** `201` with bank or IBAN coordinates.

```json
{
  "depositInstructionsId": "WmYGhs25g1GrDckzcYtpCQ",
  "receivingBankInformation": {
    "accountNumber": "237034107364",
    "routingNumber": "043087080",
    "bankName": "SSB Bank",
    "accountHolderName": "John Tester Doe"
  }
}
```

A `202` with a `Retry-After` header means the provider is still provisioning asynchronously. Poll with the **same** `X-Idempotency-Key` until you get the `201`.

<Warning>
  This endpoint takes the Meld `customerId` only. Unlike the quote endpoint, it does **not** accept `externalCustomerId` — sending one without `customerId` returns `400 [customerId] must not be blank`.
</Warning>

## Step 5 — Simulate a deposit

You cannot send real fiat to a sandbox virtual account, so nothing would trigger settlement. This endpoint creates a test deposit into the standing account from Step 4, and the provider's normal webhooks settle it exactly as in production.

| Provider | Deposit simulation | `paymentMethodType` | Fiat |
| --- | --- | --- | --- |
| Noah | Supported | `ACH` | USD |
| Due Network | Supported | `SEPA` | EUR (non-US customer) |
| Brale | Not supported | — | — |

<Warning>
  Sandbox only — in production this endpoint returns `404`. Onramp only; there is no offramp equivalent.
</Warning>

Repeat the provider, rail, currencies, and destination wallet from Step 4, and set `amount` to the amount you want deposited.

```bash
curl -s -X POST "$MELD_BASE_URL/payments/mock/headless/virtual-account/simulate-deposit" \
  -H "Authorization: BASIC $MELD_API_KEY" \
  -H "Meld-Version: $MELD_VERSION" \
  -H "Content-Type: application/json" \
  -d '{
    "customerId": "'"$CUSTOMER_ID"'",
    "serviceProvider": "NOAH",
    "paymentMethodType": "ACH",
    "sourceCurrencyCode": "USD",
    "destinationCurrencyCode": "USDC",
    "destinationWalletAddress": "0x1ab6f09b58ef63b38cee48af542561c75f2cd44c",
    "amount": "25"
  }'
```

**Expected:** `200` with a provider reference:

```json
{ "providerReference": "843ebf0d-9578-5325-8684-da21dc619338" }
```

For **Due Network**, swap in `"serviceProvider": "DUENETWORK"`, `"paymentMethodType": "SEPA"`, `"sourceCurrencyCode": "EUR"`, and a token such as `USDT_TRON`. Leave `network` out entirely for both providers; it is a Uphold-only field.

## Step 6 — Confirm settlement

Settlement is asynchronous, so the transaction does not exist yet when Step 5 returns. In a real integration you react to the `TRANSACTION_CRYPTO_*` webhooks from [Payins](/docs/stablecoins/virtual-account-integration/payins). For a scripted test, poll instead:

```bash
curl -s "$MELD_BASE_URL/payments/transactions?customerIds=$CUSTOMER_ID" \
  -H "Authorization: BASIC $MELD_API_KEY" \
  -H "Meld-Version: $MELD_VERSION" | jq '.transactions[] | {id, status, sourceAmount, sourceCurrencyCode, destinationCurrencyCode, serviceProvider, createdAt}'
```

**Expected:** `200`. The newest transaction starts at `PENDING` and reaches `SETTLED` — typically 30 to 90 seconds for Noah, sometimes longer for Due.

```json
{
  "id": "WmYGhv5xxknBWFMNppbCZ7",
  "status": "SETTLED",
  "sourceAmount": 25.0,
  "sourceCurrencyCode": "USD",
  "destinationCurrencyCode": "USDC",
  "serviceProvider": "NOAH",
  "createdAt": "2026-09-14T06:22:22.656853Z"
}
```

Re-run the command until `status` reads `SETTLED`. That is the end of the onramp flow.

A transaction carries many more fields than shown here — see [Payins → Fetch the full transaction](/docs/stablecoins/virtual-account-integration/payins#fetch-the-full-transaction) for the full shape.

## Using your own customer

Skip this if you used the pre-created customer. Use it when you want to exercise onboarding yourself.

<Warning>
  **The hosted questionnaire cannot be automated.** Meld passes the SumSub verification result to each provider, plus some standard agreement acceptances for Noah, but it never submits questionnaire answers on the customer's behalf — Due's own KYC-share request has fields for prefilled answers and Meld always sends them empty. A human must open the provider-hosted page and fill it in. There is no API-level bypass in a customer-facing environment.
</Warning>

**Create a customer.**

```bash
export CUSTOMER_ID=$(curl -s -X POST "$MELD_BASE_URL/accounts/customers" \
  -H "Authorization: BASIC $MELD_API_KEY" \
  -H "Meld-Version: $MELD_VERSION" \
  -H "Content-Type: application/json" \
  -d '{"externalCustomerId": "your-internal-user-id-123"}' | jq -r '.id')
echo "$CUSTOMER_ID"
```

**Expected:** `200` and a base58 id. For a **business** customer for KYB testing, contact Meld.

**Share SumSub KYC to the providers.** One SumSub applicant approval is reused across providers — the customer verifies identity once and Meld shares the result to each provider you name. For the full walkthrough see [KYC testing → Meld KYCes the user](/docs/stablecoins/sandbox-guide/kyc-testing).

```bash
curl -s -X POST "$MELD_BASE_URL/accounts/customers/$CUSTOMER_ID/kyc/initiate" \
  -H "Authorization: BASIC $MELD_API_KEY" \
  -H "Meld-Version: $MELD_VERSION" \
  -H "Content-Type: application/json" \
  -d '{
    "serviceProvider": "SUMSUB",
    "mode": "HOSTED_URL",
    "kycShareProviders": ["NOAH", "DUENETWORK"]
  }'
```

**Expected:** `200` with a hosted SumSub `url`. Send the customer there to complete identity verification.

A `409` means that provider was already shared. Re-issue with `PATCH` instead — it takes the **same body** as the `POST`, so `serviceProvider` and `mode` are required alongside `kycShareProviders`, and omitting them returns `400`:

```bash
curl -s -X PATCH "$MELD_BASE_URL/accounts/customers/$CUSTOMER_ID/kyc/initiate" \
  -H "Authorization: BASIC $MELD_API_KEY" \
  -H "Meld-Version: $MELD_VERSION" \
  -H "Content-Type: application/json" \
  -d '{
    "serviceProvider": "SUMSUB",
    "mode": "HOSTED_URL",
    "kycShareProviders": ["NOAH"]
  }'
```

`mode` can also be `TOKEN_IMPORT` when the customer already has a SumSub applicant or token, or `RAW_DATA_IMPORT` via the multipart variant.

**Complete the provider-hosted questionnaire.** After SumSub approval, a provider may still require its own step and sit at `PENDING`. The link lives on the customer record, at that provider's entry in `serviceProviderCustomers[]`:

```json
{
  "serviceProvider": "NOAH",
  "kyc": {
    "status": "PENDING",
    "additionalInfo": {
      "HostedURL": "https://onboarding.noah.com/...",
      "missingSteps": ["..."]
    }
  }
}
```

The questionnaire is outstanding if `kyc.additionalInfo.HostedURL` is present **and** `kyc.status` is not `APPROVED`, `REJECTED`, or `EXPIRED`. There is no separate "questionnaire complete" flag, and no intermediate "submitted, awaiting review" state — `status` moves to `APPROVED` or `REJECTED` asynchronously once the provider's webhook fires.

If a hosted link has gone stale — Due's hosted-session tokens expire — re-issue the share with the `PATCH` above, then re-fetch the customer for the fresh `HostedURL`.

<Note>
  **Due Network terms of service.** Due maintains its own terms acceptance, separate from KYC, and a customer can be KYC-approved with terms still outstanding. Re-issuing the share with the `PATCH` above refreshes it: Meld re-reads Due's account and, while the terms are pending, writes the current link to `serviceProviderCustomers[].kyc.additionalInfo.TosURL` on the customer record.

  The link is **not** in the `PATCH` response — that returns the SumSub URL. Re-fetch `GET /accounts/customers/{customerId}` and read `TosURL` from there.

  **Unverified.** This mechanism is confirmed in Meld's implementation but was not exercised against sandbox: on the account used to check this page Due's KYC sat at `PENDING`, so the terms step was never reached.
</Note>

<Warning>
  **Known gotcha (Due).** Due also runs its own KYC/KYB approval independent of the questionnaire. A customer can complete the hosted page and still be rejected by Due at order time (`err_kyc_not_passed`) if Due's account import has not completed on their side. If it persists, contact Meld.
</Warning>

## Troubleshooting

| Response | Cause |
| --- | --- |
| `403 WHITELABEL_NOT_ENABLED` | Whitelabel mode is not enabled on your account. Contact Meld. |
| `403 KYC_NOT_COMPLETED` | That provider's KYC for this customer is not `APPROVED` — often because KYC was never shared to it. Re-check Step 2, then [Using your own customer](#using-your-own-customer). |
| `400 [customerId] must not be blank` | You sent `externalCustomerId` to a provisioning or simulation endpoint. Those take `customerId` only. |
| `400 Unexpected character ('/')` | A JSON body picked up a comment. JSON does not support comments — strip them. |
| `400 ... currently supports only ...` | That provider has no sandbox deposit simulator, for example Brale. |
| `404` on simulate-deposit | You are calling production, where this endpoint does not exist. |
| `NO_VALID_QUOTES` | No provider serves that corridor and rail for your account. Check against [Provider test values](#provider-test-values). |
| `200` but nothing settles | The provider accepted it and the webhook is in flight. Keep polling Step 6. |

## Testing tips

- **Wallet addresses:** any valid address for the token's chain. Some providers validate the format matches — a TRON address for `USDT_TRON`, for example.
- **Start with the onramp (buy) flow.** It is the only path that reaches `SETTLED` in sandbox.
- **Discover currencies and rails:** call `GET /network-partner/supported/currencies` with `type=CRYPTO`, the partner name, and `category=CRYPTO_VIRTUAL_ACCOUNT_ONRAMP` (or `CRYPTO_VIRTUAL_ACCOUNT_OFFRAMP`).
- **Idempotency:** include `X-Idempotency-Key` on provisioning requests so you can safely retry without creating duplicates.
- **Partner discovery is not account enablement.** `GET /network-partner/supported/partners` lists what the catalog supports, which can be more than what is enabled on your account.
