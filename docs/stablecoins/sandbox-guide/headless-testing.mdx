This page is for developers and QA running sandbox orders through headless card and Apple Pay. Widget flows are tested with the [White-Label API and Meld Checkout testing credentials](/docs/stablecoins/sandbox-guide/test), and virtual accounts with [Virtual Account Flow Testing Credentials](/docs/stablecoins/sandbox-guide/virtual-account-flow-testing-credentials).

## What you can verify

The order call, the capture surface appearing in your app, the [SDK](/docs/stablecoins/headless-integration/sdks)'s events, and the webhook chain. How far past that you can go depends on the provider's sandbox and the payment method.

---

## Before you start

**Base URL:** `https://api-sb.meld.io`

- A sandbox API key with payment access
- Headless onramps enabled on your sandbox account. Ask your Meld representative. Until they are, orders are refused with `403 WHITELABEL_NOT_ENABLED`
- Sandbox credentials for the provider you are testing, on your Meld sandbox account
- A webhook endpoint reachable from the internet, configured in the dashboard
- A test customer. Most providers need the customer KYC-approved: see [KYC Testing](/docs/stablecoins/sandbox-guide/kyc-testing). Stripe needs only an email

<Warning>
  Sandbox coverage is narrower than production, and a US test customer is the most common reason an otherwise correct integration returns no quotes. Quote first and use whatever country and currency pair comes back with the provider you intend to test. Stripe serves only US customers.
</Warning>

## Test the card flow

Test cards against **Banxa**. It is the provider with a published headless card sandbox, and the cards below are its.

1. Quote for your country, currency pair and amount, and pick the Banxa quote.
2. Create the order with `paymentMethodType: CREDIT_DEBIT_CARD`.
3. Mount the order in your client.
4. Pay with one of the cards below.

### Successful authorization

| Card network | Card number | CVV | Expiry date | Account type |
| --- | --- | --- | --- | --- |
| Visa | 4111 1111 1111 1111 | Any 3 digits | Any future date | Debit |
| Visa | 4242 4242 4242 4242 | Any 3 digits | Any future date | Credit |
| Mastercard | 5252 5252 5252 5258 | Any 3 digits | Any future date | Debit |
| Mastercard | 5555 5555 5555 4444 | Any 3 digits | Any future date | Credit |
| Visa / Cartes Bancaires | 4035 5000 0000 0000 | Any 3 digits | Any future date | |
| Mastercard / Cartes Bancaires | 5132 0000 0000 0000 | Any 3 digits | Any future date | |
| Cartes Bancaires | 4970 0000 0000 0008 | Any 3 digits | Any future date | |

### Failed and declined authorization

| Scenario | Card network | Card number |
| --- | --- | --- |
| Generic decline | Visa | 4000 0000 0000 0002 |
| Generic decline | Mastercard | 5100 0000 0000 0008 |
| Generic fail | Visa | 4000 0000 0000 0010 |
| Generic fail | Mastercard | 5100 0000 0000 0016 |

Run at least one decline as well as one success. A decline is the path most integrations get wrong: the surface stays mounted and the customer retries, so nothing should be torn down and no order should be credited.

<Note>
  Other providers' card sandboxes behave differently and some reject transactions that would succeed in production. Where a provider publishes test cards, they are listed under its section in [White-Label API and Meld Checkout testing credentials](/docs/stablecoins/sandbox-guide/test).
</Note>

## Test Apple Pay

**You can present the sheet in sandbox. You cannot settle a payment with it.** Treat a settled Apple Pay purchase as a production check. Stripe is the exception: see [Test Stripe](#test-stripe).

1. Quote for a country and currency pair that return a Mercuryo or Banxa Apple Pay quote, and pick it.
2. Create the order with `paymentMethodType: APPLE_PAY`.
3. Check `canPresentApplePay()`, then mount.

What to confirm:

| Check | What it proves |
| --- | --- |
| The sheet appears | The order was accepted and carries a surface the SDK could present |
| The amount and label are right | You passed the sheet inputs that match the order |
| Dismissing fires `onCancel` | Your UI returns the customer to the amount screen rather than showing a failure |

The iOS Simulator presents and authorises the sheet but cannot produce a decryptable payment token, so it exercises mounting, events and the cancel path and nothing beyond. A real device with an Apple sandbox tester account gets you a genuine authorisation, and still no settlement.

---

## Verify the result

For card, check all three. Each catches something the others do not.

| Check | What it proves |
| --- | --- |
| Webhook received | Your endpoint is reachable and your signature check passes |
| `GET /payments/transactions/{id}` | The transaction exists with the amounts you expect |
| Dashboard | The transaction is attributed to the right account and provider |

The transaction is created asynchronously, so it will not exist the instant the order call returns. Wait for `TRANSACTION_CRYPTO_PENDING`.

## Test Stripe

In sandbox, Stripe orders run in an iOS app on Meld's Stripe sandbox, with Stripe's test values, so nothing is charged. You need your own Stripe account only for production: see [Before you begin with Stripe](/docs/stablecoins/headless-integration/apple-pay#before-you-begin-with-stripe).

### Set up Stripe in sandbox

1. **Ask your Meld representative to enable Stripe** on your sandbox account. It appears under **Integrations** as **Shared Meld Integration**. Meld manages its keys and Stripe's webhooks, so you add neither.
2. **Send your Meld representative your app's bundle ID and Apple Team ID.** Stripe's SDK runs only in an app that Stripe has registered as a trusted application, and Meld has Stripe register yours.
3. **For Apple Pay, register a sandbox merchant identifier**, as in [Stripe setup](/docs/stablecoins/headless-integration/apple-pay#stripe-setup). Card orders don't need one.
4. **Build an iOS test app** on the SDK versions in [iOS SDK → Install](/docs/stablecoins/headless-integration/sdks/ios#install) or [React Native SDK → Stripe orders](/docs/stablecoins/headless-integration/sdks/react-native#stripe-orders), with the camera permission ([iOS](/docs/stablecoins/headless-integration/sdks/ios#permissions), [React Native](/docs/stablecoins/headless-integration/sdks/react-native#ios-permissions)). Configure it with `Meld.configure(environment: .sandbox)`, or `Meld.configure('sandbox')` in React Native.
5. **Create a test customer with an email.**

If order creation is refused, look the code up in [Errors on Stripe order creation](/docs/stablecoins/headless-integration/apple-pay#errors-on-stripe-order-creation). Where it says to change your Stripe integration or check with Stripe, ask your Meld representative instead.

### Stripe sandbox limits

Stripe's sandbox supports only these pairs, even when a quote lists others:

| Pair | `destinationCurrencyCode` | `destinationNetworkCode` |
| --- | --- | --- |
| USDC on Ethereum | `USDC` | `ETH` |
| USDC on Base | `USDC_BASE` | `BASE` |
| USDC on Solana | `USDC_SOLANA` | `SOLANA` |

Stripe's sandbox caps a purchase at 100 USD, fees included. The quote's `sourceAmount` is the amount you quote for plus Stripe's fees, and the order carries that total, so quote well under 100 USD.

### Stripe test values

| Step | Field | Test value |
| --- | --- | --- |
| Link sign-in | One-time code | `000000` |
| KYC | First name, last name | `John`, `Verified` |
| KYC | SSN | `000000000` |
| KYC | Address line 1 | `address_full_match` |
| KYC | State | A two-letter code for a US state other than New York, such as `WA` (not `Washington`) |
| Card | Card number | `4242 4242 4242 4242`, any future expiry date, any CVV |

For document verification, Stripe's sandbox screen lets you pick the outcome instead of uploading a document.

For Apple Pay, use a physical iPhone with a real card in Apple Wallet. Stripe's sandbox returns a test token, so the card is not charged. Stripe's and Apple's test cards cannot be added to Wallet for this.

### Run a Stripe test order

<Steps>
  <Step title="Quote">
    Call `POST /payments/crypto/quote?integrationMode=HEADLESS` with `Meld-Version: 2026-05-01`, `countryCode: US`, `sourceCurrencyCode: USD` and one of the [sandbox pairs](#stripe-sandbox-limits). Without `destinationNetworkCode`, no Stripe quote comes back. Pick the `STRIPE` quote.
  </Step>
  <Step title="Create the order">
    Call `POST /crypto/order/headless/onramp` with `serviceProvider: STRIPE`, `paymentMethodType: APPLE_PAY` or `CREDIT_DEBIT_CARD`, the quote's values, a wallet address on that network and an `X-Idempotency-Key` header. Expect `201` with `responseKind: SDK_BOOTSTRAP`. In `paymentMethodResponseDetails`, `sdkEnvironment` is `SANDBOX` and `clientConfiguration.publicKey` starts with `pk_test_`.
  </Step>
  <Step title="Run Stripe's flow">
    Mount the order from the customer's tap. Sign in to Link with `000000`, and if Stripe asks for KYC, use the [test values](#stripe-test-values).
  </Step>
  <Step title="Pay">
    Pay with the test card, or with Apple Pay on a physical iPhone. Expect `onPaymentSubmitted`. If Stripe hasn't confirmed the payment yet, the SDK reports `PAYMENT_OUTCOME_UNKNOWN` instead. Either way, unmount and check the webhooks.
  </Step>
  <Step title="Check the webhooks">
    You receive `TRANSACTION_CRYPTO_PENDING`, then `TRANSACTION_CRYPTO_TRANSFERRING`. That is a pass: Stripe's sandbox doesn't reliably report delivery, so `TRANSACTION_CRYPTO_COMPLETE` may never arrive.
  </Step>
</Steps>

No webhook reaches you until Stripe reports the payment or rejects the session. A rejected session ends in `TRANSACTION_CRYPTO_FAILED`. `POST /payments/mock/headless/simulate` doesn't work on Stripe orders: only Stripe settles them.
