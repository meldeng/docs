Use this page to test headless buys and sells in sandbox, paid by card, Apple Pay, Google Pay, bank transfer or mobile money. To test widget flows, see [White-Label API and Meld Checkout testing credentials](/docs/stablecoins/sandbox-guide/test). To test virtual accounts, see [Virtual Account Flow Testing Credentials](/docs/stablecoins/sandbox-guide/virtual-account-flow-testing-credentials).

## What you can verify

The order call, the capture surface appearing in your app, the [SDK](/docs/stablecoins/headless-integration/sdks)'s events, and the webhook chain. How far past that you can go depends on the provider's sandbox and the payment method.

You can take these orders to a final status in sandbox:

| Provider | Flow | Sandbox result |
| --- | --- | --- |
| [T-0](#t-0) | Buy | `SETTLED`, after you simulate the payment |
| [Yellow Card](#yellow-card) | Sell | `SETTLED`, `FAILED` or `REFUNDED`, chosen by the payout phone number and the customer's last name |
| [dLocal](#dlocal) | Sell | `SETTLED`, after you simulate the deposit |
| [Brale](#brale) | Sell | `SETTLED`, after you simulate the deposit |

## Before you start

**Base URL:** `https://api-sb.meld.io`

- A sandbox API key with payment access
- Headless onramps enabled on your sandbox account, and headless offramps if you test a sell. Contact Meld support to enable them. Until then, orders are refused with `403 WHITELABEL_NOT_ENABLED`
- The provider you are testing enabled on your sandbox account
- A unique `externalOrderId` for each order
- A webhook endpoint reachable from the internet, configured in the dashboard
- A test customer with an email. For Banxa and Mercuryo, also KYC-approved: for Banxa, start KYC with `BANXA` in `targetServiceProviders` and `Meld-Version: 2026-11-01`; for both, complete it as in [KYC Testing](/docs/stablecoins/sandbox-guide/kyc-testing#complete-the-sumsub-check-in-sandbox). Stripe and Coinbase need no Unified KYC. With [Level 1](/docs/stablecoins/unified-kyc/kyc-levels) on for your account, Stripe needs it at Level 1. For other providers, a `403 KYC_NOT_COMPLETED` means the provider can't take the customer yet: see [KYC Testing](/docs/stablecoins/sandbox-guide/kyc-testing)

In the examples, replace `<YOUR_API_KEY>` with your sandbox API key and `<CUSTOMER_ID>` with your test customer's `id`.

<Warning>
  Sandbox coverage is narrower than production, and a US test customer is the most common reason an otherwise correct integration returns no quotes. Quote first and use whatever country and currency pair comes back with the provider you intend to test. Stripe serves only US customers.
</Warning>

## Test the card flow

Test cards against **Banxa**. It is the provider with a published headless card sandbox, and the cards below are its.

1. Quote for your country, currency pair and amount, and pick the Banxa quote.
2. Create the order with `paymentMethodType: CREDIT_DEBIT_CARD`.
3. Mount the order in your client.
4. Pay with one of the cards below.

<Warning>
  Banxa card orders don't complete in sandbox. Contact Meld support before you test this flow.
</Warning>

Banxa also needs the customer's acceptance of its terms. Record it, or send `verification.agreementAcceptedAt` on the create request: see [Legal agreements](/docs/stablecoins/headless-integration/shared-flows/eligibility#legal-agreements). Without it, the order is refused with `403 LEGAL_ACCEPTANCE_REQUIRED`.

### Successful authorization

| Card network | Card number | CVV | Expiry date | Account type |
| --- | --- | --- | --- | --- |
| Visa | 4111 1111 1111 1111 | Any 3 digits | Any future date | Debit |
| Visa | 4242 4242 4242 4242 | Any 3 digits | Any future date | Credit |
| Mastercard | 5252 5252 5252 5258 | Any 3 digits | Any future date | Debit |
| Mastercard | 5555 5555 5555 4444 | Any 3 digits | Any future date | Credit |
| Visa / Cartes Bancaires | 4035 5000 0000 0000 | Any 3 digits | Any future date | |
| Mastercard / Cartes Bancaires | 5132 0000 0000 0000 | Any 3 digits | Any future date | |
| Cartes Bancaires | 4970 0000 0000 0008 | Any 3 digits | Any future date | |

### Failed and declined authorization

| Scenario | Card network | Card number |
| --- | --- | --- |
| Generic decline | Visa | 4000 0000 0000 0002 |
| Generic decline | Mastercard | 5100 0000 0000 0008 |
| Generic fail | Visa | 4000 0000 0000 0010 |
| Generic fail | Mastercard | 5100 0000 0000 0016 |

Run at least one decline as well as one success. A decline is the path most integrations get wrong: the surface stays mounted and the customer retries, so nothing should be torn down and no order should be credited.

<Note>
  Other providers' card sandboxes behave differently and some reject transactions that would succeed in production. Where a provider publishes test cards, they are listed under its section in [White-Label API and Meld Checkout testing credentials](/docs/stablecoins/sandbox-guide/test).
</Note>

## Test Apple Pay

Two options in sandbox:

- **Mercuryo or Banxa:** you can present the sheet, but not settle a payment. Treat a settled purchase as a production check.
- **Stripe:** you can run the whole purchase, with Stripe's test values, and nothing is charged.

### Apple Pay with Mercuryo or Banxa

1. Quote for a country and currency pair that return a Mercuryo or Banxa Apple Pay quote, and pick it.
2. Create the order with `paymentMethodType: APPLE_PAY`. Mercuryo can refuse it with `400 INVALID_PAYMENT_METHOD` when its native sheet can't open for that IP and corridor: see [Errors on order creation](/docs/stablecoins/headless-integration/wallets#errors-on-order-creation).
3. Check the quote row's [readiness](/docs/stablecoins/headless-integration/wallets#2-check-each-row-on-the-device) before you show the button, then mount the order from a tap.

| Check | What it proves |
| --- | --- |
| The sheet appears | The order was accepted and carries a surface the SDK could present |
| The amount and label are right | You passed the sheet inputs that match the order |
| Dismissing fires `onCancel` | Your UI returns the customer to the amount screen rather than showing a failure |

The iOS Simulator presents and authorises the sheet but can't produce a decryptable token, so it exercises mounting, events and the cancel path only. A real device with an Apple sandbox tester account gets a genuine authorisation, and still no settlement.

### Apple Pay with Stripe

Stripe orders run in an iOS app on Meld's Stripe sandbox. Card orders run the same way, with `paymentMethodType: CREDIT_DEBIT_CARD` and no Apple setup.

**Setup:**

1. Ask your Meld representative to enable Stripe on your sandbox account. It appears under **Integrations** as **Shared Meld Integration**, and Meld manages its keys and webhooks.
2. Send your Meld representative your app's bundle ID and Apple Team ID, so Stripe registers the app as a trusted application. Stripe's SDK runs only in a registered app, on a simulator too.
3. For Apple Pay, register a sandbox merchant identifier, as in [Stripe's certificate](/docs/stablecoins/headless-integration/wallets#stripes-certificate).
4. Build the test app on the [iOS SDK](/docs/stablecoins/headless-integration/sdks/ios#install) or [React Native SDK](/docs/stablecoins/headless-integration/sdks/react-native#ios), with the camera permission, configured for `sandbox`.
5. Create a test customer with an email. If the customer is also KYC-approved, Meld fills Stripe's KYC. Otherwise, type the test values below when Stripe asks.

**Limits.** Stripe's sandbox caps a purchase at 100 USD, fees included, so quote well under it. It supports only USDC on Ethereum (`USDC` / `ETH`), Base (`USDC_BASE` / `BASE`) and Solana (`USDC_SOLANA` / `SOLANA`), even when a quote lists other pairs.

**Test values:**

| Step | Field | Value |
| --- | --- | --- |
| Link sign-in | One-time code | `000000` |
| KYC | First name, last name | `John`, `Verified` |
| KYC | SSN | `000000000` |
| KYC | Address line 1 | `address_full_match` |
| KYC | State | A two-letter code other than `NY`, such as `WA` |
| Card | Card number | `4242 4242 4242 4242`, any future expiry, any CVV |

For document verification, Stripe's sandbox lets you pick the outcome instead of uploading a document. For Apple Pay, use a physical iPhone with a real card in Wallet: Stripe's sandbox returns a test token, so the card isn't charged.

**Run it:**

1. Quote with `integrationMode=HEADLESS`, `countryCode: US`, `sourceCurrencyCode: USD` and one of the pairs above, including `destinationNetworkCode`. Pick the `STRIPE` quote.
2. Create the order. Expect `201` with `responseKind: SDK_BOOTSTRAP`.
3. Mount it from the customer's tap. Sign in to Link with `000000`, and use the test values if Stripe asks for KYC.
4. Pay. Expect `onPaymentSubmitted`, or `PAYMENT_OUTCOME_UNKNOWN` if Stripe hasn't confirmed yet. Either way, unmount.
5. Expect `TRANSACTION_CRYPTO_PENDING`, then `TRANSACTION_CRYPTO_TRANSFERRING`. That's a pass: Stripe's sandbox doesn't reliably report delivery, so `TRANSACTION_CRYPTO_COMPLETE` may not arrive.

A refused session ends in `TRANSACTION_CRYPTO_FAILED`. `POST /payments/mock/headless/simulate` doesn't apply to Stripe orders.

## Test bank transfer and mobile money

### Simulate a payment or deposit

No money moves in sandbox. To complete a T-0, dLocal or Brale order, simulate its payment or deposit:

```bash
curl -s -X POST "https://api-sb.meld.io/payments/mock/headless/simulate" \
  -H "Authorization: BASIC <YOUR_API_KEY>" \
  -H "Content-Type: application/json" \
  -d '{ "externalOrderId": "my-order-001" }'
```

**Expected:** `200` with the order's `transactionId`.

### T-0

Send the originator and beneficiary names for the travel rule in `providerData.travelRuleData`.

```bash
curl -s -X POST "https://api-sb.meld.io/crypto/order/headless/onramp" \
  -H "Authorization: BASIC <YOUR_API_KEY>" \
  -H "Content-Type: application/json" \
  -d '{
    "customerId": "<CUSTOMER_ID>",
    "externalOrderId": "my-order-001",
    "serviceProvider": "TZERO",
    "paymentMethodType": "ACH",
    "sourceCurrencyCode": "USD",
    "sourceAmount": 100,
    "destinationCurrencyCode": "USDT",
    "destinationNetworkCode": "ETH",
    "destinationWalletAddress": "0x1ab6f09b58ef63b38cee48af542561c75f2cd44c",
    "countryCode": "US",
    "providerData": {
      "travelRuleData": {
        "originator": [{ "naturalPerson": { "name": { "nameIdentifier": [{
          "primaryIdentifier": "Tester",
          "secondaryIdentifier": "Example",
          "nameIdentifierType": "NATURAL_PERSON_NAME_TYPE_CODE_LEGL"
        }] } } }],
        "beneficiary": [{ "naturalPerson": { "name": { "nameIdentifier": [{
          "primaryIdentifier": "Tester",
          "secondaryIdentifier": "Example",
          "nameIdentifierType": "NATURAL_PERSON_NAME_TYPE_CODE_LEGL"
        }] } } }]
      }
    }
  }'
```

**Expected:** `201` with `responseKind: RECEIVING_BANK_DETAILS`. Without `travelRuleData`, the order is refused with `400 TRANSACTION_MISSING_SERVICE_PROVIDER_DETAILS`.

Then [simulate the payment](#simulate-a-payment-or-deposit) and [check the transaction](#verify-the-result). Expect `SETTLED`.

### Yellow Card

Choose the outcome with the last 10 digits of `fiatPayoutMethod.details.phoneNumber`. For a refund, also create the test customer with `name.lastName` set to `RefundSuccess`. The payout's own `lastName` doesn't change the outcome.

| Outcome | `fiatPayoutMethod.details.phoneNumber` | Customer's `name.lastName` | Order status |
| --- | --- | --- | --- |
| Success | `+2541111111111` | Any | `SETTLED` |
| Failure | `+2540000000000` | Any except `RefundSuccess` | `FAILED` |
| Refund | `+2540000000000` | `RefundSuccess` | `REFUNDED` |

Give the customer an email address. Without one, the order is refused with `400 CUSTOMER_EMAIL_REQUIRED`.

Before your first Yellow Card order, contact Meld support to link your test customer to Yellow Card. Until it is linked, the order is refused with `404 NOT_FOUND` and the message `ServiceProviderCustomer not found`.

```bash
curl -s -X POST "https://api-sb.meld.io/crypto/order/headless/offramp" \
  -H "Authorization: BASIC <YOUR_API_KEY>" \
  -H "Content-Type: application/json" \
  -d '{
    "customerId": "<CUSTOMER_ID>",
    "serviceProvider": "YELLOWCARD",
    "externalOrderId": "my-order-002",
    "sourceCurrencyCode": "USDT_TRON",
    "destinationCurrencyCode": "KES",
    "sourceAmount": 10,
    "countryCode": "KE",
    "sourceWalletAddress": "TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t",
    "fiatPayoutMethod": {
      "type": "MOBILE_MONEY",
      "details": {
        "firstName": "Jane",
        "lastName": "Tester",
        "phoneNumber": "+2541111111111"
      }
    }
  }'
```

**Expected:** `201` with `status: AWAITING_DEPOSIT`. You don't need to send crypto: the order reaches its final status within seconds. [Check the result](#verify-the-result).

To get a quote first, send the corridor to `POST /payments/partner/quote` with the payout amount in `destinationAmount`. This endpoint refuses `sourceAmount` with `400 BAD_REQUEST`.

```bash
curl -s -X POST "https://api-sb.meld.io/payments/partner/quote" \
  -H "Authorization: BASIC <YOUR_API_KEY>" \
  -H "Content-Type: application/json" \
  -d '{
    "serviceProviders": ["YELLOWCARD"],
    "sourceCurrencyCode": "USDT_TRON",
    "destinationCurrencyCode": "KES",
    "destinationAmount": 1000,
    "countryCode": "KE"
  }'
```

**Expected:** `200` with a `YELLOWCARD` quote. If you get `408 QUOTE_TIMEOUT`, Yellow Card's sandbox was slow to answer: send the request again.

### dLocal

Identify the bank with a Meld bank code in `fiatPayoutMethod.details.bankIdentifier`. If you send `bankCode` instead, the order is refused with `400 BENEFICIARY_DETAILS_INVALID`.

```bash
curl -s -X POST "https://api-sb.meld.io/crypto/order/headless/offramp" \
  -H "Authorization: BASIC <YOUR_API_KEY>" \
  -H "Content-Type: application/json" \
  -d '{
    "customerId": "<CUSTOMER_ID>",
    "serviceProvider": "DLOCAL",
    "externalOrderId": "my-order-003",
    "sourceCurrencyCode": "PYUSD_SOLANA",
    "destinationCurrencyCode": "COP",
    "sourceAmount": 100,
    "countryCode": "CO",
    "fiatPayoutMethod": {
      "type": "PAYOUT_TO_BANK",
      "details": {
        "accountNumber": "1234567890",
        "bankIdentifier": { "type": "BANK_DIRECTORY_CODE", "value": "BANCOLOMBIA" },
        "bankAccountType": "SAVINGS",
        "documentType": "NATIONAL_ID",
        "documentId": "1020304050",
        "purpose": "FAMILY_SUPPORT",
        "flowType": "B2C",
        "accountHolderType": "INDIVIDUAL",
        "firstName": "Juan",
        "lastName": "Duarte",
        "beneficiaryAddress": {
          "streetLineOne": "Calle 100 # 10-20",
          "city": "Bogota",
          "country": "CO"
        }
      }
    }
  }'
```

**Expected:** `201` with `status: AWAITING_DEPOSIT`. Then [simulate the deposit](#simulate-a-payment-or-deposit) and [check the result](#verify-the-result). Expect `SETTLED`.

### Brale

Brale pays out by `ACH` to a US bank account.

```bash
curl -s -X POST "https://api-sb.meld.io/crypto/order/headless/offramp" \
  -H "Authorization: BASIC <YOUR_API_KEY>" \
  -H "Content-Type: application/json" \
  -d '{
    "customerId": "<CUSTOMER_ID>",
    "serviceProvider": "BRALE",
    "externalOrderId": "my-order-004",
    "sourceCurrencyCode": "USDC",
    "destinationCurrencyCode": "USD",
    "sourceAmount": "0.01",
    "countryCode": "US",
    "sourceWalletAddress": "0x1ab6f09b58ef63b38cee48af542561c75f2cd44c",
    "fiatPayoutMethod": {
      "type": "ACH",
      "details": {
        "accountHolderName": "Test Tester",
        "bankAccountType": "CHECKING",
        "routingNumber": "021000021",
        "accountNumber": "000555443210",
        "bankName": "Test Bank"
      }
    }
  }'
```

**Expected:** `201` with `status: AWAITING_DEPOSIT`. Then [simulate the deposit](#simulate-a-payment-or-deposit) and [check the result](#verify-the-result). Expect `SETTLED`.

If you get `422 SERVICE_PROVIDER_ERROR`, Brale has disabled that bank account after a failed transfer. Use a different account number.

## Verify the result

Get the order's transaction:

```bash
curl -s "https://api-sb.meld.io/payments/transactions?orderIds=<ORDER_ID>" \
  -H "Authorization: BASIC <YOUR_API_KEY>"
```

Replace `<ORDER_ID>` with the `id` from the create response.

For card, check all three. Each catches something the others do not.

| Check | What it proves |
| --- | --- |
| Webhook received | Your endpoint is reachable and your signature check passes |
| `GET /payments/transactions/{id}` | The transaction exists with the amounts you expect |
| Dashboard | The transaction is attributed to the right account and provider |

The transaction is created asynchronously, so it will not exist the instant the order call returns. Wait for `TRANSACTION_CRYPTO_PENDING`.
