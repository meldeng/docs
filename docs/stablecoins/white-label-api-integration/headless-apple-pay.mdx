Meld supports headless Apple Pay, where you can launch the Apple Pay card of the provider directly in your application. This is great for first time users to be able to buy crypto as easily as possible.

Headless Apple Pay is available through two providers, and each one has a different integration model:

| Provider | Integration model | What you build |
| --- | --- | --- |
| [Mercuryo](#mercuryo) | Native Apple Pay JS on your own domain | Apple Pay JS event handlers that proxy through two Meld endpoints |
| [Coinbase](#coinbase) | Coinbase-hosted Apple Pay payment link | OTP-verify the user via Coinbase's Verification API, one order call, then render the returned link (iframe on web, direct launch on mobile) |

Both paths deliver the same UX goal: the user taps Apple Pay and the payment sheet opens — no second or intermediate screen.

## Mercuryo

Mercuryo headless Apple Pay runs a native `ApplePaySession` on your own domain. Users can make transactions up to \$700 (total) using headless Apple Pay with Mercuryo without having to KYC. After this threshold, users will have to KYC with Mercuryo in order to continue buying crypto.

### Phase 1 — Domain registration (one-time, with Meld)

1. **Pick the domain** where the Apple Pay sheet will run (e.g., pay.yourcompany.com). It must be HTTPS with a valid certificate. Subdomains are fine, but each one is registered separately.
2. **Send the domain to Meld** via your integration contact.
3. **Meld adds your domain to our Apple Pay Merchant ID** (merchant.io.meld.cryptowidget) in Apple Developer.
4. **Meld sends you the domain association file** — a small binary blob Apple issues for your specific domain.
5. **You host the file** at the exact path:
   ```text
   https://pay.yourcompany.com/.well-known/apple-developer-merchantid-domain-association
   ```
   Requirements:
   - HTTP 200, no redirects.
   - Bytes returned must be byte-for-byte identical to the file we sent — no minification, no whitespace tweaks, no transformation.
   - Content-Type doesn't strictly matter but text/plain or application/octet-stream is safe.
   - Publicly reachable (no auth, no IP restrictions).
6. **Confirm with Meld** the file is live. Meld clicks **Verify** in Apple Developer → status goes from Pending to Verified.
7. **Meld asks Mercuryo to add your domain** to the NAP widget's Additional URL list. (Once.)

After Phase 1, your domain is set up for life (Apple's verification typically lasts ~6 months and re-verifies automatically as long as the file stays live).

### Phase 2 — Implement Apple Pay on your domain (one-time, in your frontend)

1. **Call our session endpoint** when the user is ready to pay:
   ```text
   POST https://api.meld.io/crypto/session/widget
   ```
   In the response, check isNativeApplePaySupported (or equivalently look at whether serviceProviderWidgetUrl points at meldcrypto.com vs exchange.mercuryo.io).
2. **If** isNativeApplePaySupported: true — your page implements Apple Pay JS:
   - From a user click handler, construct new ApplePaySession(version, paymentRequest).
   - Implement onmerchantvalidation:
     - POST the validationURL (Apple gives you in the event) to our endpoint:
       ```text
       POST https://api.meld.io/crypto/session/mercuryo/apple-pay/validate-merchant
       Body: { "validationURL": "<the URL Apple gave you>" }
       Header: X-Crypto-Session-Token: <session token from step 1>
       ```
     - Pass the returned merchantSession to session.completeMerchantValidation(merchantSession).
   - Implement onpaymentauthorized:
     - POST the encrypted Apple Pay token \+ buyer info to:
       ```text
       POST https://api.meld.io/crypto/session/mercuryo/apple-pay/process
       Body: { payToken, buyToken, email, firstName, lastName, billingAddress, address, ip, merchantTransactionId }
       Header: X-Crypto-Session-Token: <session token>
       ```
     - On success (status is pending / paid / completed) → call session.completePayment(ApplePaySession.STATUS\_SUCCESS).
     - If response includes redirect\_url → call session.completePayment(ApplePaySession.STATUS\_FAILURE) and redirect the user to that URL (Mercuryo's hosted widget, where they finish the payment).
     - On any other failure → STATUS\_FAILURE and show an error.
3. **If** isNativeApplePaySupported: false — no Apple Pay JS needed. Just open the serviceProviderWidgetUrl from the session response (it'll point to Mercuryo's hosted widget). User completes the payment there.

### What Meld handles for you (so you don't have to)

- mTLS to Apple's startSession endpoint (your onmerchantvalidation POSTs to us, we do the secure call to Apple, we return merchantSession).
- Forwarding the Apple Pay token to Mercuryo's /native-mobile-pay endpoint.
- Handling Mercuryo's response shape (success vs redirect\_url).
- Renewing the Merchant Identity cert and Apple's annual cert chain rotations.

You only need to: serve the well-known file, and implement the Apple Pay JS event handlers that proxy through our two endpoints.

### Why not just iframe meldcrypto.com?

Apple Pay has strict restrictions on iframe origins — the sheet checks the _parent_ frame's domain. So even if you iframe our hosted widget, Apple still validates against your domain, and you'd still need the same Phase 1 work. There's no shortcut.

## Coinbase

Coinbase headless Apple Pay works differently: there is no Apple Pay JS to implement, no domain association file to host, and no merchant validation to proxy. You OTP-verify the customer's phone and email through Coinbase's Onramp Verification API (verifications stay valid for 60 days), then create a headless order with one API call, and Meld returns a Coinbase-hosted payment link that renders the Apple Pay button. Embed that link inline in your checkout (web) or launch it directly (iOS, Android) — the user's only step is confirming in the Apple Pay sheet.

<Warning>
  **Requirements**

  - **US only.** Coinbase guest checkout is available to US users with a US phone number. It must be a real cell number — VoIP numbers are rejected.
  - **Verified email and phone.** The customer's email address and phone number must both be OTP-verified through Coinbase's Onramp Verification API before the order is created, and the resulting verification ids must be sent on the order (see Step 1 below).
  - **Guest limits.** Coinbase enforces a weekly spending cap and a lifetime maximum of 15 guest checkout transactions per user. Beyond those limits, the user must continue with a full Coinbase account.
  - **Domain allow-listing.** To render the payment link in an iframe on web, the parent page's domain must be allow-listed with Coinbase. Send the domain to Meld via your integration contact before you go live.
</Warning>

### Step 1 — Verify the customer's contact details

Verification runs on Coinbase's rails: for each channel it is a two-step call to Coinbase's Onramp Verification API — initiate sends the user a 6-digit OTP, submit exchanges that code for a verification id. **Both channels — SMS and email — must be verified**, and each verification id is valid for **60 days**, after which you re-verify.

1. **Initiate** — `POST https://api.cdp.coinbase.com/platform/v2/onramp/verifications` with the channel (`SMS` or `EMAIL`) and the destination (E.164 phone number or email address). Coinbase sends a 6-digit OTP to the destination and returns a `verificationId`.
2. **Submit** — `POST https://api.cdp.coinbase.com/platform/v2/onramp/verifications/{verificationId}/submit` with the `otpCode` the user received. On success the verification is marked verified and the response carries the `verificationId` and its `verificationExpiresAt` (60 days out).

Run the two steps once per channel: the SMS submit yields your `smsVerificationId`, the email submit yields your `emailVerificationId`. Separately, record the ISO-8601 timestamp at which the user accepted Coinbase's guest-checkout terms as `agreementAcceptedAt`. All three values go on the order in Step 2.

See Coinbase's [Headless Onramp docs](https://docs.cdp.coinbase.com/onramp/headless-onramp/overview) and the [Submit onramp verification API reference](https://docs.cdp.coinbase.com/api-reference/v2/rest-api/onramp/submit-onramp-verification) for the full contract.

### Step 2 — Create a headless order

When the user is ready to pay, create a headless order with `serviceProvider: "COINBASEPAY"` and `paymentMethodType: "APPLE_PAY"`:

```text
POST https://api.meld.io/crypto/order/headless/onramp
```

This is the same generic headless-order endpoint the other headless providers use.

```json
{
  "customerId": "WXDsY9TDMhKGYyNu9CH9W7",
  "serviceProvider": "COINBASEPAY",
  "paymentMethodType": "APPLE_PAY",
  "countryCode": "US",
  "sourceAmount": 100,
  "sourceCurrencyCode": "USD",
  "destinationCurrencyCode": "USDC_BASE",
  "destinationWalletAddress": "0xfCFAa8059080D01b27ccA2B1fA086df0853397E6",
  "customerPhoneNumber": "+12025550123",
  "externalOrderId": "your-order-ref-123",
  "clientIpAddress": "203.0.113.10",
  "verification": {
    "smsVerificationId": "onramp_verification_11111111-2222-3333-4444-555555555555",
    "emailVerificationId": "onramp_verification_66666666-7777-8888-9999-000000000000",
    "agreementAcceptedAt": "2026-07-28T12:00:00Z"
  }
}
```

| Field | Notes |
| --- | --- |
| `countryCode` | Required. Must be `US` — Coinbase headless onramp is US-only. |
| `sourceAmount` / `sourceCurrencyCode` | Fiat amount and currency the user pays. USD only. |
| `destinationCurrencyCode` | Crypto the user receives, network-qualified where applicable (e.g. `USDC_BASE`). |
| `destinationWalletAddress` | Destination wallet address for the purchased crypto. |
| `customerPhoneNumber` | The user's phone number (E.164, US cell) — send the same number you verified over SMS in Step 1. Falls back to the phone on the Meld customer record if omitted. |
| `externalOrderId` | Your order reference; forwarded to Coinbase as the partner order reference. |
| `clientIpAddress` | End-user IP, forwarded to Coinbase. |
| `verification.smsVerificationId` | Verification id from the SMS channel's submit call in Step 1 (`onramp_verification_<uuid>`, valid 60 days). |
| `verification.emailVerificationId` | Verification id from the email channel's submit call in Step 1 (`onramp_verification_<uuid>`, valid 60 days). |
| `verification.agreementAcceptedAt` | ISO-8601 timestamp at which the customer accepted Coinbase's guest-checkout terms. |

The customer's **email is not sent in the request body** — Meld pulls it from the Meld customer record, so make sure the record carries the address you verified in Step 1.

<Note>
  The `verification` block is optional on the generic headless-order endpoint (other providers
  ignore it) but **required for Coinbase Apple Pay**. If any of its three fields is missing — or
  the request resolves to no phone number or no email at all — Meld rejects the order with an HTTP
  400 validation error that names each missing field (e.g. `verification.smsVerificationId`,
  `verification.emailVerificationId`, `verification.agreementAcceptedAt`) before anything is sent
  to Coinbase.
</Note>

A successful request returns the headless-order envelope with a Coinbase-hosted Apple Pay payment link nested under `paymentMethodResponseDetails`:

```json
{
  "paymentMethodType": "APPLE_PAY",
  "paymentMethodResponseDetails": {
    "paymentLinkUrl": "https://pay.coinbase.com/..."
  }
}
```

### Step 3 — Launch the payment link

**Web** — embed the link in an iframe with `allow="payment"`:

```html
<iframe
  src="{paymentLinkUrl}"
  allow="payment"
  style="border: none; width: 100%; height: 48px;"
/>
```

The user taps to pay and the Apple Pay sheet opens over your page — there is no intermediate screen. The parent page's domain must be allow-listed with Coinbase, or the link will not render.

### Step 4 — Detect completion

On web, the payment link posts messages to the parent window as the payment progresses:

| Event | Meaning |
| --- | --- |
| `onramp_api.commit_success` | The user authorized the payment and the order was submitted. |
| `onramp_api.polling_success` | The transaction was confirmed. Safe to show your success state. |
| `onramp_api.cancel` | The user dismissed the Apple Pay sheet. Return them to your quote/checkout. |
| `onramp_api.commit_error` / `onramp_api.polling_error` / `onramp_api.load_error` | The payment or the hosted page failed. Show an error / retry option. |

{/* TODO(NPI:COINBASEPAY) [VERIFY] The cancel and failure event names are sandbox-unverified — confirm the exact names against crypto-widget-web#239's sandbox pass before publishing. */}

Always validate the message origin before trusting it — a payment-completion signal must not be spoofable by another frame on your page — and handle both string and object payloads (Coinbase may post the event name as a raw string):

```javascript
// Derive the trusted origin from the payment link you embedded.
const expectedOrigin = new URL(paymentLinkUrl).origin;

window.addEventListener("message", (event) => {
  if (event.origin !== expectedOrigin) return; // ignore other frames/windows
  if (event.source !== iframeEl.contentWindow) return; // only the frame we embedded

  let name;
  if (typeof event.data === "string") {
    try {
      name = JSON.parse(event.data)?.eventName ?? event.data;
    } catch {
      name = event.data; // raw event-name string
    }
  } else {
    name = event.data?.eventName;
  }

  if (name === "onramp_api.commit_success") {
    // payment authorized — show progress state
  }
  if (name === "onramp_api.polling_success") {
    // transaction confirmed — show success state
  }
});
```

<Warning>
  Because a cancelled sheet produces no webhook, don't rely on `polling_success` alone to unblock
  your UI — also implement a timeout or poll the transactions endpoint so a user who cancels or hits
  an error isn't stuck waiting.
</Warning>

Treat postMessage events as a UI signal only. The authoritative transaction status comes from Meld webhooks and the transactions endpoint, same as any other white-label transaction.

### Sandbox testing

- Use the sandbox base URL `https://api-sb.meld.io` with your sandbox API key.
- For the Step 1 OTP verification, use the sandbox test values: a `+1000`-prefixed phone number (e.g. `+10005550100`), an email address ending in `@sandbox.test`, and the OTP code `000000`.
- Sandbox orders always succeed, so you can exercise the full flow end to end.
- Sandbox `paymentLinkUrl` values **already include** `useApplePaySandbox=true` (Meld appends it server-side from the environment) — embed the link as-is. Do not add it yourself, or you'll double the parameter.
- Meld also applies Coinbase's required `sandbox-` partner-user-reference prefix automatically in sandbox — no integrator action needed.

Because the partner user reference is built from the Meld customer id, Coinbase's guest-checkout caps (weekly cap and 15-lifetime-transaction maximum) accrue **per Meld customer**.
