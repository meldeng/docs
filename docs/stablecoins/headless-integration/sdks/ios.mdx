title: "iOS SDK"
description: "Mount a provider’s payment surface into a view you own, or present a native Apple Pay sheet."
---

The SDK is a container and an event relay. It does not render card input or carry card data; capture happens on the provider's own surface.

Building in React Native? Use the [React Native SDK](/docs/stablecoins/headless-integration/sdks/react-native) instead; it wraps this one.

---

## Install

**Swift Package Manager.** In Xcode: **File → Add Package Dependencies…**, paste the repository URL and add the **MeldSDK** library to your app target.

```swift
dependencies: [
    .package(url: "https://github.com/meldeng/meldsdk-ios", from: "0.9.1"),
],
targets: [
    .target(name: "YourApp", dependencies: [
        .product(name: "MeldSDK", package: "meldsdk-ios"),
    ]),
]
```

**CocoaPods.**

```ruby
pod 'MeldSDK', '~> 0.9.1'
```

Then `import MeldSDK`.

```swift
Meld.configure(environment: .sandbox) // or .qa, .production
```

Configure the environment your backend created the order in. When the SDK continues an order by calling Meld from the device, as it does for Stripe, it calls the configured environment's host.

## Create the order on your backend

The order comes from your server. Your API key never ships in the app binary.

See [Cards](/docs/stablecoins/headless-integration/cards) or [Apple Pay](/docs/stablecoins/headless-integration/apple-pay) for the request.

## Mount the order

```swift
let handle = try Meld.mount(order, into: containerView, handlers: MeldEventHandlers(
    onReady:            { _ in hideSpinner() },
    onPaymentSubmitted: { _ in showProcessing() },
    onStatusChange:     { status in track(status) },
    onCancel:           { _ in showRetryCta() },
    onError:            { error in show(error.message) }
))
```

Apple Pay uses the same call with an `applePay:` argument — see [Apple Pay](/docs/stablecoins/headless-integration/apple-pay).

Keep the handle until the user finishes paying. Releasing it tears the surface down, and `handle.unmount()` does the same on demand.

## Events

| Event | Meaning |
| --- | --- |
| `onReady` | The surface has loaded |
| `onStatusChange` | Carries a normalized status: `pending`, `completed`, `failed` or `cancelled` |
| `onPaymentSubmitted` | The user finished paying. Unmount and show processing. **Not settlement** |
| `onCancel` | The user backed out, or dismissed the Apple Pay sheet |
| `onError` | Carries a code and message |

[The five events](/docs/stablecoins/headless-integration/sdks#the-five-events) covers what each one means, and how `onCancel` and `onError` relate to the status.

### Error codes

`onError` carries a `code` and a `message`, plus a `detail` with the provider's own event or code when the SDK has one.

| `code` | Meaning |
| --- | --- |
| `APPLE_PAY_UNAVAILABLE` | Apple Pay cannot be presented. No attempt exists: offer another method |
| `PRESENTATION_FAILED` | The flow stopped before any payment. No attempt exists; the next attempt needs a new order |
| `PAYMENT_REJECTED` | Declined, and nothing will settle. Offer another option |
| `ORDER_STATE_CHANGED` | The provider no longer accepts this order. No attempt exists |
| `VERIFICATION_PENDING` | The provider is still reviewing the customer. No attempt exists |
| `PAYMENT_OUTCOME_UNKNOWN` | A payment may exist. Track the order through your backend and never pay it again |

`error.attemptMayExist` is `false` only for the first five. Treat any other code, including one a later SDK release adds, as a payment that may exist: track the order and never pay it again.

## Permissions

Providers that run KYC inside their surface need camera access, and so does Stripe's identity check. Declare `NSCameraUsageDescription` in your `Info.plist` with a string that explains the document and selfie capture. Without it, that step fails silently for the user, or, on a Stripe order, the SDK refuses it.

Apple Pay needs the Apple Pay capability on your target, with the merchant identifier you registered. See [Apple Pay](/docs/stablecoins/headless-integration/apple-pay).

---

## Stripe orders

A Stripe order runs Stripe's own SDK inside this one: Link sign-in, Stripe's identity checks, then Apple Pay or Stripe's card form. `MeldSDK` brings in Stripe's `StripeCryptoOnramp`, pinned to 26.11.x, so another dependency on a different Stripe iOS release will not resolve alongside it. What the order carries is in [Apple Pay → Stripe](/docs/stablecoins/headless-integration/apple-pay#stripe).

Mount it with the same `Meld.mount` call; `into:` and `applePay:` are optional, and an `applePay:` you pass must match the order's amount, in `USD`.

The SDK shows nothing of its own until it needs the customer, and `onReady` fires before anything is on screen. Keep your own busy state — a spinner on the button that started the purchase — until a terminal callback, and block anything that would unmount the SDK or start another order meanwhile. Unmounting reports no outcome.

Errors use the [codes above](#error-codes). On `PAYMENT_REJECTED`, `detail` says why: `submission:FAILED`, `submission:EXPIRED`, `create:PROVIDER_REJECTED` or `create:START_NEW_ORDER`. When the flow stops on a refused call, `detail` names the refusal, such as `action:AUTHORIZATION_REQUIRED`.

## Settlement

Settlement is your webhook. `onPaymentSubmitted` fires when the user finishes paying, which is earlier: unmount and show a pending state until the webhook arrives.

See [Configure webhooks](/docs/stablecoins/headless-integration/shared-flows/configure-webhooks).
