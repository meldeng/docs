---
title: "iOS SDK"
description: "Mount a provider’s payment surface into a view you own, or present a native Apple Pay sheet."
---

The SDK is a container and an event relay. It does not render card input or carry card data; capture happens on the provider's own surface.

Building in React Native? Use the [React Native SDK](/docs/stablecoins/headless-integration/sdks/react-native) instead; it wraps this one.

---

## Install

The SDK supports iOS 15 and later.

**Swift Package Manager.** In Xcode: **File → Add Package Dependencies…**, paste the repository URL and add the **MeldSDK** library to your app target.

```swift
dependencies: [
    .package(url: "https://github.com/meldeng/meldsdk-ios", from: "0.9.1"),
],
targets: [
    .target(name: "YourApp", dependencies: [
        .product(name: "MeldSDK", package: "meldsdk-ios"),
    ]),
]
```

**CocoaPods.**

```ruby
pod 'MeldSDK', '~> 0.9.1'
```

Then `import MeldSDK`.

`MeldSDK` brings in two dependencies of its own, whichever providers you use: Stripe's `StripeCryptoOnramp`, pinned to 26.11.x (patch releases only), and `PrimerSDK` 2.x, from 2.49. If your app already depends on a different minor release of Stripe's iOS SDK, the two will not resolve together.

## Configure the environment

```swift
Meld.configure(environment: .sandbox) // or .production
```

Configure the environment your backend created the order in, once, before you mount: `.sandbox` for orders created on `https://api-sb.meld.io`, `.production` for `https://api.meld.io`. The SDK defaults to `.sandbox`.

When the SDK continues an order by calling Meld from the device, as it does for Stripe, it calls the configured environment's host. It also refuses a Stripe order from the other environment: `Meld.capabilities(for:)` reports `unsupported`, and `Meld.mount` throws.

## Create the order on your backend

The order comes from your server. Your API key never ships in the app binary.

See [Cards](/docs/stablecoins/headless-integration/cards) or [Apple Pay](/docs/stablecoins/headless-integration/apple-pay) for the request. Return the response to the app unchanged: the SDK reads what it needs from it.

## Mount the order

```swift
let order = try MeldOrder.from(jsonData: responseData) // your backend's response, unchanged

guard Meld.capabilities(for: order).surface != "unsupported" else {
    // This build cannot present the order. Offer another method.
    return
}

let handle = try Meld.mount(order, into: containerView, handlers: MeldEventHandlers(
    onReady:            { _ in hideSpinner() },  // not on a Stripe order, see Stripe orders
    onPaymentSubmitted: { _ in showProcessing() },
    onStatusChange:     { status in track(status) },
    onCancel:           { _ in showRetryCta() },
    onError:            { error in if !error.recoverable { endCheckout(error) } }
))
```

Call `mount` on the main thread. Pass `into:` a view you own for an embedded card widget. Apple Pay and Stripe orders draw nothing into it, because the SDK presents them itself, so `into:` is optional for them.

Apple Pay uses the same call with an `applePay:` argument — see [Apple Pay](/docs/stablecoins/headless-integration/apple-pay).

Keep the handle until a terminal callback. Releasing it tears the surface down, and `handle.unmount()` does the same on demand. Neither delivers a callback.

To check a quote before you create the order, decode its `headlessPresentation` with `MeldHeadlessPresentation(json:)` and pass it, with the `paymentMethodType`, to `Meld.capabilities(for:paymentMethodType:)`. That tells you only whether this build can present that kind of order. Check the order itself again before you mount it.

## Events

| Event | Meaning |
| --- | --- |
| `onReady` | The surface has loaded, or the Apple Pay sheet is opening. On a Stripe order it fires before anything is on screen |
| `onStatusChange` | Carries a normalized status: `pending`, `completed`, `failed` or `cancelled` |
| `onPaymentSubmitted` | The user finished paying. Unmount and show processing. **Not settlement** |
| `onCancel` | The user backed out, or dismissed the Apple Pay sheet. Nothing will settle |
| `onError` | Carries a `code`, a `message`, `recoverable` and `detail` |

[The five events](/docs/stablecoins/headless-integration/sdks#the-five-events) covers what each one means, and how `onCancel` and `onError` relate to the status.

Each mount delivers exactly one terminal callback: `onPaymentSubmitted`, `onCancel`, or `onError` with `recoverable: false`. Nothing follows it, and a retry needs a new order. Releasing the handle before one ends the mount with no callback.

### Error codes

`onError` carries a `code` and a `message`, plus a `detail` with the provider's own event or code when the SDK has one. Log `detail`; don't branch on it.

`recoverable: true` comes only from an embedded card widget, for example `PROVIDER_LOAD_FAILED`. The widget stays up and the customer can carry on, so it is not terminal. Embedded card widgets keep their own codes.

Apple Pay and Stripe orders report these normalized codes. Mercuryo Apple Pay can also report codes of its own, which the rule below the table covers.

| `code` | Meaning |
| --- | --- |
| `APPLE_PAY_UNAVAILABLE` | Apple Pay cannot be presented. No attempt exists: offer another method |
| `PRESENTATION_FAILED` | The flow stopped before any payment. No attempt exists; the next attempt needs a new order |
| `PAYMENT_REJECTED` | Declined, and nothing will settle. Offer another option |
| `ORDER_STATE_CHANGED` | The provider no longer accepts this order. No attempt exists |
| `VERIFICATION_PENDING` | The provider is still reviewing the customer. No attempt exists |
| `PAYMENT_OUTCOME_UNKNOWN` | A payment may exist. Track the order through your backend and never pay it again |

`error.attemptMayExist` is `false` only for the first five. When `recoverable` is `false`, treat any other code as a payment that may exist, including a provider's own code and one a later SDK release adds: track the order and never pay it again.

## Permissions

Providers that run KYC inside their surface need camera access, and so does Stripe's identity check. Declare `NSCameraUsageDescription` in your `Info.plist` with a string that explains the document and selfie capture. Without it, that step fails silently for the user, or, on a Stripe order, the SDK refuses it and the flow ends in `onError`.

Apple Pay needs the Apple Pay capability on your target, with your merchant identifier, whenever the sheet is presented under your identifier: Mercuryo, Banxa and Stripe today. List every identifier an order can carry. For Stripe, list both your sandbox and your live merchant identifier. Each Stripe environment issues its own CSR, so each needs its own identifier: see [Stripe setup](/docs/stablecoins/headless-integration/apple-pay#stripe-setup). Coinbase needs no identifier and no entitlement, because it presents the sheet as merchant of record. See [Apple Developer setup](/docs/stablecoins/headless-integration/apple-pay#apple-developer-setup).

## Stripe orders

A Stripe order runs Stripe's own SDK inside this one: Link sign-in, Stripe's identity checks, then Apple Pay or Stripe's card form. What the order carries is in [Apple Pay → Stripe](/docs/stablecoins/headless-integration/apple-pay#stripe).

Mount it with the same `Meld.mount` call. `into:` and `applePay:` are optional. An `applePay:` you pass must match the order's amount, in `USD`, or `mount` throws. Its `summaryItemLabel` labels the Apple Pay sheet.

Without `into:`, the SDK presents from your app's only foreground window. In an app with several windows, pass `into:` a view in the window you want it to present from.

The SDK shows nothing of its own until it needs the customer, and `onReady` fires before anything is on screen. Keep your own busy state — a spinner on the button that started the purchase — until a terminal callback, and block anything that would unmount the SDK or start another order meanwhile. Unmounting reports no outcome.

One Stripe order runs at a time. After you unmount a Stripe order, the SDK can take up to 90 seconds to release Stripe's SDK. A Stripe order you mount before then reports `PRESENTATION_FAILED`, so an immediate retry on a new order can fail.

Stripe's SDK works only in an app that Stripe has registered as a trusted application, on a simulator too. Live orders need a physical device. When you run one from Xcode, set the `com.apple.developer.devicecheck.appattest-environment` entitlement to `production`.

Errors use the [codes above](#error-codes). On `PAYMENT_REJECTED`, `detail` says why: `submission:FAILED`, `submission:EXPIRED`, `create:PROVIDER_REJECTED` or `create:START_NEW_ORDER`. When the flow stops on a refused call, `detail` names the refusal, such as `action:AUTHORIZATION_REQUIRED`.

Not every refusal reports `PAYMENT_REJECTED`. Once the device has started the payment, a refusal the SDK cannot classify reports `PAYMENT_OUTCOME_UNKNOWN`. Track that order through your backend, as the table says.

## Coinbase orders

A Coinbase Apple Pay order presents Coinbase's Apple Pay sheet, with Coinbase as merchant of record. You set up nothing with Apple for it. What the order carries is in [Apple Pay → Coinbase](/docs/stablecoins/headless-integration/apple-pay#coinbase).

It needs iOS 16 or later. Below that, `Meld.capabilities(for:)` reports `unsupported` and `Meld.mount` throws, so don't offer it.

Mount it with the same `Meld.mount` call, on the main thread, from the customer's tap on your Apple Pay button. `into:` is optional, and `applePay:` is ignored. If you pass `into:`, keep that view in its window until a terminal callback. If the view leaves its window first, the SDK ends the order with no callback.

The customer sees only the Apple Pay sheet, and `onReady` fires as it opens. If no screen is visible to present from, `mount` throws. On a device that cannot make Apple Pay payments, `mount` returns, then `onError` reports `APPLE_PAY_UNAVAILABLE`.

| What happens | Callback |
| --- | --- |
| Coinbase accepts the payment | `onStatusChange` with `pending`, then `onPaymentSubmitted` |
| The customer dismisses the sheet before paying | `onCancel` |
| Apple Pay is not available or not set up for this customer | `onError` with `APPLE_PAY_UNAVAILABLE` |
| Coinbase no longer accepts the order, for example because it was already used or has expired | `onError` with `ORDER_STATE_CHANGED`. Create a new order |
| Coinbase declines the payment | `onError` with `PAYMENT_REJECTED` |
| Coinbase's page does not load, the sheet does not open, or Coinbase reports any other error | `onError` with `PRESENTATION_FAILED` |
| Coinbase reports an error while checking the payment, its page fails after the sheet was requested, or no outcome arrives within 180 seconds. Time the sheet is on screen does not count | `onError` with `PAYMENT_OUTCOME_UNKNOWN`. Track the order and never pay it again |

Every error ends the mount. `detail` carries Coinbase's event and code, for example `onramp_api.load_error:ERROR_CODE_GUEST_APPLE_PAY_NOT_SUPPORTED`.

You can release the handle on `onPaymentSubmitted`. The SDK gives Coinbase up to 60 seconds to finish confirming the payment on its own.

This SDK version cannot present a sandbox Coinbase order: mounting one ends in `onError` with `PRESENTATION_FAILED`, and nothing is charged. In sandbox, test up to order creation, as in [Test Coinbase in sandbox](/docs/stablecoins/headless-integration/apple-pay#test-coinbase-in-sandbox). Test the sheet itself in production, on a physical iPhone on iOS 16 or later that can make Apple Pay payments.

## Settlement

Settlement is your webhook. `onPaymentSubmitted` fires when the user finishes paying, which is earlier: unmount and show a pending state until the webhook arrives.

See [Configure webhooks](/docs/stablecoins/headless-integration/shared-flows/configure-webhooks).
